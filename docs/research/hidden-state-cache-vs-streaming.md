# Getting target hidden states to the drafter trainer: disk cache vs streaming

Research for ticket #11 (map #1). Compiled 2026-10-08. Three threads, synthesized: DeepSpec's cache mechanics (verified against the `deepseek-ai/DeepSpec` source at `005e03b` — the exact SHA the proxy run pinned), TorchSpec's streaming design (official repo, PyTorch blog, adopter writeups), and Modal platform bounds (official docs and pricing, retrieved 2026-10-08). Decouples from the audit doc's estimate where the code disagrees with it.

## Answer in one paragraph

**Train run one on DeepSpec's disk-cache path. On Modal, streaming loses on economics — and not only for the reason the fog assumed.** The decision turns on two platform facts that changed or were measured only now: Modal began billing network egress on 2026-10-01 ($0.04/GiB beyond the plan allowance, and container-to-container private traffic — the wire a streaming design uses — counts), while Volume reads and writes are explicitly egress-free; and TorchSpec's production streaming mode re-runs the teacher forward pass **once per epoch**, because its Mooncake store is a bounded staging buffer (tens of GiB), not a corpus cache. At the DeepSpec recipe (10 epochs over ~1.3e9 tokens), streaming re-generates ~64 TB of hidden states ten times: roughly $9k–18k of teacher GPU-hours plus ~$23k of egress — either alone is budget-scale, together fatal. The disk cache pays the teacher once, reads back egress-free, and is reusable by every later run that shares the layer set (stage-C retrains, the DFlash/Eagle3 arms, the sequential-head A/B). Plain terms: a cache records the teacher's lecture once and replays the tape for each study session — storage costs rent, replays are free. Streaming makes the teacher re-teach live before every session and pays a per-byte toll on every replay. Run the tape. The genuine streaming advantage survives in one named fallback: a stream-once, single-epoch recipe (~$2.3k egress, no storage) if Volume bandwidth or storage cost ever bites — but it changes the training recipe, not just the plumbing, and DeepSpec hard-wires the cache path, so it is fallback, not default.

## 1. What DeepSpec's disk cache actually is (code-verified)

- **One path only.** The public repo's training data surface is exactly `CacheDataset` + `CacheCollator`; `BaseTrainer.__init__` hard-wires `CacheDataset(cache_dir=self.args.data.target_cache_path)` and no streaming alternative exists anywhere in the package. The DSpark paper's O(d) hidden-state-communication variant lives in DeepSeek's internal HAI-LLM framework and is absent from the public code ([deepspec-audit.md](deepspec-audit.md) already noted this; re-confirmed at source).
- **Format**: per full sequence (prompt + response, real tokens only), stored as 64-GiB binary shards (`shard-NNNNN.bin`) + a 56-byte-per-sample index (`samples.idx`) + a validating `manifest.json`. Five tensors per sample: `input_ids` (int32), `attention_mask` + `loss_mask` (uint8), `target_hidden_states` (bf16, `seq_len × m × hidden`), and **`target_last_hidden_states` (bf16, `seq_len × hidden`)** — the extra stream exists so the trainer can compute TV-loss target logits locally through the frozen LM head (the paper's O(d) trick, partially preserved).
- **The audit's size estimate is ~⅙ low.** The cache stores **(m + 1) streams, not m**. At hidden 4096, bf16: 6 streams = 49,158 B/token → **63.9 TB at 1.3e9 tokens** (not 50–60); 4 streams (3 layers) = 32,774 B/token → **42.6 TB** (not ~32); 8 streams (7-layer union) = 65,542 B/token → **85.2 TB**. Sanity anchors: the in-tree "roughly 38 TB" warning for Qwen3-4B and the proxy's measured 611 GB both land within a few percent of this formula.
- **bf16 only, no fp8 path.** `TARGET_CACHE_HIDDEN_DTYPE = "bfloat16"` is a module constant; the manifest validator asserts it; repo-wide search for fp8 returns nothing. Quantizing the cache is a custom protocol patch (writer cast, dtype constant, manifest assert, reader view), not a flag.
- **The build is not resumable and has no GC.** `prepare_target_cache.py` raises on a non-empty output dir (the proxy run hit this gotcha — stale dirs must be deleted by hand, e.g. `modal volume rm -r`). Plan the GLM cache build as a chunked/resumable wrapper from day one.
- **Training re-reads the cache once per epoch — 10× read amplification** — and anchor packing happens on GPU at train time (`num_anchors=512` sampled per sequence per step over the full cached sequence). Every cached token's hidden states are consumed each epoch (draft blocks attend over the whole context before their anchor).
- **Reuse semantics**: the manifest binds cache↔config on `target_layer_ids`, `hidden_size`, `target_model_name_or_path` only — nothing about head architecture or run name. One cache serves DSpark, DFlash, and Eagle3 trainers alike; stage-C retrains and the sequential-head A/B share it for free. A different layer set (e.g. the 7-layer union for the top-3 arm) needs a new cache.
- **The proxy measured the build cheap**: 611 GB (19,817 samples, ~19.9M tokens, layers [1,9,17,25,33] + last-hidden stream) in **~55 min / $3.62 on 1×H100** — derived ~6.1k tok/s, overhead-dominated (~5% MFU: per-sample Python serialization and CPU bf16 copies, not compute). Measured training read rate at proxy scale: ~0.76 GB/s aggregate across 4 ranks, no recorded I/O stalls.
- **mHC does not change the math unless the wrapper lets it.** The Qwen3 wrapper captures exactly one stream per layer (the layer module's first output tensor). GLM's 4-branch mHC makes "the layer-l hidden state" a choice — capture one branch or a fold per layer and the cache stays at (m+1) streams; capture all 4 branches and it multiplies ~3.5× (~168+ TB at 1.3e9 tokens, ~$15.5k/mo held — ruled out by economics before engineering). The wrapper spike (drafter-design decision) must land on a single stream per layer.

## 2. What streaming actually is (TorchSpec)

- **Mechanism**: Ray-orchestrated, disaggregated. The target runs inside production engines (vLLM Worker Extension, patched SGLang, TRT-LLM `SaveHiddenStates` redirect); hidden states are written zero-copy into a central **Mooncake** DRAM object store (K3 recipe: 512 GB segment, 16 GB local buffer, hard-pinned, one-shot consumption — force-deleted after fetch) and fetched by FSDP2 training workers. Target logits are never transferred — recomputed from last hidden states via the LM head, same trick as DeepSpec's extra stream.
- **The load-bearing fact: streaming mode re-runs the teacher per epoch.** At each epoch boundary the controller logs "Dataset exhausted, reloading" and re-dispatches the whole corpus to the engines; consumed tensors are deleted from Mooncake; there is no memoization. Mooncake is a transfer bus with a bounded window, not a cache. The LightSeek K3 writeup states the coupling plainly: "whichever side is slower throttles the other."
- **The escape hatch is offline replay — which is a disk cache.** `torchspec.offline.generate` materializes hidden states to disk (resumable, ~6 GB per 1,000 Qwen3-8B samples), reusable "for as many training runs as needed" — but the docs warn it is "not optimized for throughput yet" and lacks USP/train-with-decode support. TorchSpec's own no-storage answer to the cache problem is to rebuild the cache.
- **DSpark training is real and exercised**: merged 2026-06-29, same loss shape as DeepSpec (CE 0.1 / L1 0.9 / confidence 1.0, γ=7, 512 anchors, 5 layers, rank-256 Markov head); end-to-end on Kimi K3 with released checkpoints (`lightseekorg/kimi-k3-dspark`, `Inferact/Kimi-K3-DSpark`). Caveats from the authors: the K3 DSpark drafter trained for fewer epochs than its DFlash2 sibling ("not a fully matched comparison"), an early DSpark trainer was "mostly vibe-coded" (PR #129), a norm-layer bug was fixed (issue #169), and a DSpark quality drop on a larger target is on record (issue #190, Qwen3-14B trains "much worse" than 4B) — GLM-5.3-Flash is a much larger target.
- **Family surface is engine-centric, and GLM has a head start**: if the engine runs the target, TorchSpec needs only tensor-key mappings (`embedding_key`/`lm_head_key`/`norm_key`), a draft-architecture JSON, and a chat renderer — and a `glm45` renderer is already registered (grammar "shared 4.5 → 5.2"). A DSpark drafter against a GLM target already exists — `RedHatAI/GLM-5.2-speculator.dspark`, trained via the sibling vLLM Speculators library with the same Mooncake streaming mechanism — which materially de-risks the family question, though for GLM-5.2 (dense-sparse attention, no mHC), not GLM-5.3-Flash's hybrid KDA + sparse MLA + mHC layout. SGLang is TorchSpec's "best community effort" tier; GLM-5.3-Flash's best serving story is SGLang (engines doc), so the GLM-5.3 engine hook is the unproven piece.
- **Adoption evidence is broad but the GLM-5.3-shaped hole remains**: DigitalOcean (MiniMax-M2.5 EAGLE3), CoreWeave (Kimi K2.7 DFlash), fal (DSpark, Ideogram V4, 16× throughput), Tencent (AngelSpec), Artificial Analysis (EAGLE3). Nobody has streamed a hybrid linear-attention + mHC target.

## 3. Modal platform bounds (2026-10, official docs)

- **Volumes**: $0.09/GiB-month, 1 TiB/month free; no documented capacity cap ("not block devices and do not have a fixed capacity" — sharding across Volumes is not required, only file/inode hygiene); designed for "up to 2.5 GB/s" bandwidth, not guaranteed; daily snapshot billing, deletion billed up to 4 more days; ≤ ~5 concurrent writers recommended on v1 (v2 is Beta — "cannot yet guarantee that no data will be lost" — stick to v1 for a one-writer cache build). **Volume reads and writes do not count as network egress.**
- **Ephemeral disk (the prior doc's unmeasured number)**: 512 GiB default quota, **3.0 TiB hard max**, billed by raising the memory request 20:1 (full 3 TiB ≈ 150 GiB memory ≈ $1.20/hr). It cannot hold the cache at any scale this effort contemplates, and it does not survive between jobs — the dataset-ingestion guide's copy-to-Volume-and-commit pattern exists precisely because of this.
- **Egress billing is live (2026-10-01, first bill Nov 1)**: $0.04/GiB beyond the workspace allowance (Starter 1 TiB/mo, Team 10 TiB/mo), and the scope explicitly "includes … private network traffic sent directly to other Modal containers" — the i6pn path a streaming design would use (documented ≥ 50 Gbps, region-scoped). Bucket writes through CloudBucketMounts also count as egress; Volume I/O and bucket downloads do not.
- **Timeouts and preemption**: 24 h per execution attempt (retry = fresh clock); **all GPU Functions are preemptible by default and `nonpreemptible` is not supported for GPU Functions** — long jobs checkpoint into Volumes or die. Both a multi-24 h cache build and multi-day training must checkpoint to a Volume.
- **Clusters are GA (2026-10-01)** — the GPU guide's "private beta (email us)" sentence is stale. Up to 32 nodes / 256 GPUs with a 3,200–6,400 Gbps RDMA fabric; teacher + trainer on one cluster is now a first-class shape. (Whether intra-cluster RDMA traffic is exempt from egress billing is not documented — see Gaps.)
- **Concurrency**: Team plan ($250/mo) = 50 concurrent GPUs — teacher node + trainer node + eval node concurrently does not fit Starter's 10. Whether the $250 fee draws against credit grants remains undocumented (prior open question, still open).
- **RAM buffering is priced like compute**: memory is $0.008/GiB-hr, so holding ~1 TiB of hidden states in RAM ≈ $8.19/hr — same order as a GPU-hour. Mooncake-style DRAM staging on Modal buys nothing over a Volume.

## 4. The cost model (GLM-5.3-Flash, 1.3e9 cached tokens, 6 streams)

| | Bytes/token | Cache size | Storage $/mo held | Teacher passes | Egress |
|---|---|---|---|---|---|
| **Disk cache, 5 layers** | 49,158 | 63.9 TB | ~$5.1k | 1 | 0 |
| Disk cache, 3 layers | 32,774 | 42.6 TB | ~$3.4k | 1 | 0 |
| Disk cache, 7-layer union | 65,542 | 85.2 TB | ~$6.9k | 1 | 0 |
| Stream, 10 epochs | — | never stored | 0 | 10 (36–72 node-h each) | ~$23k |
| Stream, 5 epochs | — | never stored | 0 | 5 | ~$11.4k |
| Stream, 1 epoch | — | never stored | 0 | 1 | ~$2.3k |

Derived arithmetic over confirmed unit rates: storage = GiB × $0.09 net of the free TiB; egress = (TiB − 10) × 1,024 × $0.04 on Team; teacher pass = 1.3e9 tokens at the assumed-but-unmeasured 5–10k tok/s/node (modal-cost.md L123) → 36–72 node-h ≈ $0.9–1.8k per pass on a 4×B200/B300-class node. Per 1e9 cached tokens at 5 layers: ~49.2 TB ≈ **$3.9k/mo held** — the number that prices ticket #22's data-scale decision.

Hold-time scenarios (5 layers, 1.3e9 tokens): ~$2.4k for two weeks, ~$5.1k for a month. The cache is a rent, and rent scales with hold time — build, train, delete, and only hold across the window where retrains plausibly need it.

## 5. Decision

**Disk cache, on the DeepSpec path, for run one.** Reasons, in order of weight:

1. **Epoch economics**: the recipe's 10 epochs turn any per-epoch re-forward into a 10× teacher spend and any streaming wire into a 10× egress bill. The cache amortizes the teacher pass to once and reads back free.
2. **Platform fit**: Volume I/O is egress-free and capacious enough; container-to-container streaming is taxed exactly where streaming is heavy. Modal's pricing rewards the cache shape.
3. **Implementation risk asymmetry**: DeepSpec's cache path is the battle-tested default (proxy run reproduced it end to end); streaming GLM-5.3-Flash would need the TorchSpec GLM-5.3 engine hook (its SGLang tier is "best community effort") plus the same family wrapper work, on a stack whose DSpark-vs-large-target record has one known quality incident (issue #190).
4. **Reuse**: the cache outlives run one — stage-C retrains, the sequential-head A/B (ticket #14's proxy A/B already rides the kept Qwen cache), and any DFlash/Eagle3 arm share it at zero marginal capture cost.

## 6. Levers if the cache gets expensive (named, in priority order)

1. **Hold-time discipline** (free): delete the cache when the iteration window closes; two weeks ≈ $2.4k, a month ≈ $5.1k at full scale.
2. **Data scale** (ticket #22's lever): the cache is linear in tokens — every 1e9 tokens costs ~$3.9k/mo held at 5 layers. The data-mix decision now carries this price tag explicitly.
3. **Fewer captured layers** (config-only): 3 layers → 42.6 TB (~$3.4k/mo). The capture spread is a drafter-design hyperparameter (ticket #8's [1,12,23,34,44]); cutting to 3 is a retrain-judged change, not free, but the cache math is exactly linear.
4. **fp8 cache protocol patch** (custom engineering, halves storage to ~$2.6k/mo): DeepSpec is bf16-hard-coded; a small patch to the writer/reader/manifest. Worth it only if holding time × size gets painful.
5. **Cache home: R2 via CloudBucketMount instead of a Modal Volume** (unverified read throughput): R2 Standard is $0.015/GB-mo (63.9 TB ≈ $900/mo vs $5.1k) and mount **downloads are ingress** (egress-free); the one-shot cache **write** through the mount is egress (~$2.3k beyond Team's allowance) and Mountpoint has filesystem limitations (no append/seek-write — fine for write-once shards). Breakeven in under a week of holding. Verify read bandwidth on Modal before committing.
6. **Stream-once, single-epoch fallback** (recipe change, not plumbing): ~$2.3k egress + one teacher pass, no storage — only if Volume bandwidth or storage cost actually bites, and only with the data-hunger curve's blessing (more data at fewer epochs is exactly the direction the proxy curve points).
7. **The 7-layer union, captured once if run-2 is plausible**: 85.2 TB (~$6.9k/mo) buys both arms (run-1 spread + top-3 layers 42–44) from a single stage-B pass, versus two sequential 63.9 TB caches. Only worth it if the top-3 arm is live; decides with the fog item it is coupled to.

## 7. Risks and mitigations

- **Volume bandwidth vs the 10-epoch re-read**: 10 epochs × 63.9 TB = 639 TB of reads. At the 2.5 GB/s design ceiling that needs ≥ ~3 days of wall time for the training stage alone; if stage-C compute really fits in ~1 day (the audit's optimistic-FLOP estimate), the Volume throttles training by ~3×. Mitigation: measure sustained read rate in the first hour of training; if read-bound, drop to 5 epochs (the K3 DSpark recipe's own choice) and/or 3 layers, or move the cache to R2 (lever 5). This is a run-one measurement, not a new decision ticket.
- **Preemption**: GPU functions cannot opt out; a killed cache build loses everything (no resume) unless wrapped. Mitigation: chunk the GLM cache build across executions with per-chunk manifest merge, and checkpoint training to the same Volume (DeepSpec already checkpoints every 3,000 steps).
- **Single-writer discipline**: v1 Volumes recommend ≤ ~5 concurrent writers and no locking; the cache build is naturally single-writer if the GLM wrapper writes shards from one rank rather than per-rank temp dirs.
- **mHC stream capture**: multiplies the cache ~3.5× if all branches are captured — economically ruled out up front; the wrapper spike pins the single stream (or fold) per layer, coupled to the drafter-design decision's open mHC question.
- **fp8 target, bf16 cache**: the cache stores bf16 hidden states from an FP8 target — matches DeepSpec's convention (bf16 activations out of FP8 checkpoints) and the audit's noise-term assessment of FP8 on τ; no cache-side action.
